# 交付前自检清单

**两个 HTML 都生成后，逐项过一遍。** 不通过就改，不要交付。

## 0. 用户输入与交付一致性

- [ ] HTML 里所有 POI 都来自**用户提供的数据**，没添加用户没说过的地点
- [ ] 行程天数 / 日期 / 顺序与用户原话一致
- [ ] 火车/航班号 / 时间与用户提供的一致
- [ ] 酒店名 / 地址 / 入住日期与用户订单一致

## 1. 数据真实性（最关键）

- [ ] 每个 TRIP 的 `lng / lat` 都在 `poi-candidates.md` 里有 ✅ 记录
- [ ] 没有 ⚠️ 待确认 / ❌ 搜不到的 POI 直接进了 HTML
- [ ] 没有写"约 ¥X" "大概 X 分钟"这类模糊表述
- [ ] 酒店名称与用户订单**完全一致**（不能简写）
- [ ] 火车/航班号已向用户确认
- [ ] 营业时间 / 门票价格与官方信息一致（不要凭印象）
- [ ] desc 字段不超过 30 字，没加主观形容词

## 2. 必查项（用坐标反查 POI 名）

对每个 POI 打开高德 App，把坐标输进去，看跳出来的名字和 HTML 里写的：
- [ ] 名字对得上
- [ ] 类型对（酒店 → 酒店 POI，不能跳到居民楼）
- [ ] 步行距离 / 周边描述对得上
- [ ] 城市没串（佛山 POI 不会跳到广州）

## 3. HTML 完整性

- [ ] TRIP 数组每条都有 `day, time, type, icon, name, desc, city, lng, lat` 8 个字段
- [ ] TRANSIT_HINTS 的 key 数量与 TRIP 中需要交通衔接的段数匹配（不是必须每段都有，但填了的要核对）
- [ ] HOTELS 数组每条都有 `order` 字段且唯一（如果用了酒店 tab）
- [ ] DAY_META 覆盖所有出现的 day 编号
- [ ] WEATHER_COORDS 的 day 编号覆盖 TRIP 里出现过的 day
- [ ] TRIP_DATES 数组长度 >= 行程天数
- [ ] AMAP_KEY / AMAP_SECURITY 已替换为用户提供的（**不是模板里的占位**）
- [ ] 没有遗留模板里的"祖庙"等示例数据

## 4. 渲染测试

- [ ] 浏览器打开 desktop 版，所有 Day 卡片都能展开/折叠
- [ ] 点击 POI，右侧详情浮层正常显示
- [ ] 切换 Tab（全程 / 交通 / 酒店），内容正确切换
- [ ] 切换 Day pill，地图 markers 跟着变
- [ ] 手机浏览器（DevTools 模拟）打开 mobile 版，布局没溢出
- [ ] 移动版点底部"打开地图"按钮，地图浮层正常
- [ ] 点 POI 卡片进入详情浮层，"高德 App →"链接能正常打开

## 5. 配色检查

- [ ] 主色用墨绿 `#1f3d34`（除非用户明确要求换色系）
- [ ] 类别色按 schema 使用
- [ ] 没有用 emoji 装饰地点名（地名后不要加 🏛️ 🦁 这类）
- [ ] 卡片间距 ≥ 8px
- [ ] 字体层级清晰（标题 14-26px，正文 12-14px）

## 6. 文案检查

- [ ] 没有"小镰仓""日系小清新"等网梗
- [ ] 没有"超赞""必去""绝美"等营销词
- [ ] 没有"🔥🔥🔥"等营销符号（用户原文留的 🔥 保留，不要新增）
- [ ] 没有主观形容词（"很美""值得"）
- [ ] 没有"五星""4.5 分"等评分
- [ ] 没有给景点加 emoji 装饰

## 7. 已知陷阱（不同行程的踩坑点）

### 7.1 key 偏移问题
TRANSIT_HINTS 的 key 是 `day:N`，指向**该 POI 的下一段交通**。

### 7.2 次日时间
写成字符串 "次日 06:42"，**不要**写 "30:42" 这种数学计算结果。

### 7.3 高德 POI 搜不到的常见类型
- "XX 汽车站" → 试 "XX 客运站"、"XX 客运中心"
- "XX 火车站" → 试 "XX 站"（很多是小站名）
- 通用品类词（"陶艺DIY"、"按摩"、"咖啡"）→ 几乎搜不到，要问用户具体店名

### 7.4 用户提供的地点名要完整保留
如果用户说"XX 国际酒店（XX 广场 XX 地铁站店）"，**整串都用**，不能简写成"XX 酒店"。同理：餐厅、景点、店名——按用户原话保留括号、修饰词、地标限定。

### 7.5 国内外不要混用
高德地图只显示国内，国外行程要么换 Google Maps，要么删地图模块。

## 8. 不要做的事（重复提醒）

- ❌ 不要为没搜到的 POI 编一个"看起来合理"的坐标
- ❌ 不要把同类别的不同 POI 用同一个坐标（即使在同一片区域）
- ❌ 不要在 desc 字段写 emoji 装饰
- ❌ 不要给用户做行程"优化建议"（除非用户主动问）
- ❌ 不要把这次会话的数据保留到下次（每次新建 `poi-candidates.md`）

## 9. 交付格式

给用户两个独立文件：
- `<行程名>.html`（桌面版）
- `<行程名>-mobile.html`（移动版）

文件名用拼音或简短中文，**不要用 v1.0 / v2.0 这种版本号**，除非用户特别要求。

附带：
- `poi-candidates.md` — 坐标来源表，用户可以查到所有 POI 的出处
- （可选）一个简短的 `changes-log.md`，记录这次做了什么调整
