# 审计完整性运行手册

## 背景

一次 129-skill 审计暴露出一个高风险问题：3 个并行分组只产出 106 条，且组间有重复；后续把汇总数组按固定切片重写 group 文件会掩盖遗漏/重复，使“文件存在、JSON 可解析”被误认为审计完整。

## 强制流程

1. 从 `skills_list()` 取得清单，保存唯一 expected 集合：`name -> category`。不要手工按记忆计数。
2. 分组时使用不重叠集合，并立即验证：
   - `len(group1)+len(group2)+len(group3) == len(expected)`
   - `set(group1) | set(group2) | set(group3) == set(expected)`
   - 三组两两交集为空。
3. 子代理完成后，分别验证每个 JSON：可解析、条目数正确、字段齐全、名称集合与该组 expected 集合完全相等。若只报告“字段完整”但条目数不符，必须重审缺失项。
4. 若发现遗漏，新增补审组或重跑该组；不要把其他组结果通过数组切片写回原 group 文件。切片只能用于临时合并产物，不能替代分组校验。
5. 合并前做全局断言：
   - 总条目数等于 expected 数；
   - 名称集合完全相等且无重复；
   - 每条 `category` 与 catalog 一致；
   - 幽灵 skill 明确标记 `closure=0`、`SKILL NOT FOUND`，而不是与“未审计”混淆。
6. 生成 HTML/JSON 后再次验证文件存在、HTML 非空、汇总 JSON 条目数和唯一名称数正确。

## 常见陷阱

- **代理声称 43 条但实际 36 条**：以磁盘 JSON 的机器校验为准，不信 summary。
- **重复分组**：按类别边界分组时容易把前一组尾部复制到后一组；必须检查交集。
- **幽灵与遗漏混淆**：skill_view 失败才可标记幽灵；未出现在任何结果中的名称仍是“未审计”，应补审。
- **错误的补救**：把完整汇总数组按 `data[i*43:(i+1)*43]` 写回 group 文件会制造看似完整但语义错误的分组。应保留原始 group 文件，单独生成 merged 输出。

## 验收标准

只有同时满足“数量正确、集合正确、无重复、字段完整、幽灵可解释、最终产物可读”才算审计完成。
