# Presentation Defense（创新大赛答辩与现场问答）

## When to Use（何时使用）

当用户提供 PPT、讲稿或方案材料，要求进行创新大赛、项目答辩、路演、评审会的提问预测、压力审查、现场口径准备或问答文档整理时使用。

## 核心目标

把方案材料转换成评委能在现场快速理解、参评人能直接背诵的回答。重点不是堆技术名词，而是让回答同时具备：

1. **事实边界**：明确哪些已经实现、哪些只是构思或计划，绝不虚构指标和上线情况。
2. **具体闭环**：回答“谁产生结果、结果是什么、谁核验、如何使用、何时不能使用”。
3. **评委适配**：科技评委关注数据模型、系统边界、可解释性和验证；业务评委关注收益、流程、客户和合规。
4. **现场可用**：每个重点问题给出 20—35 秒标准版，必要时再给十几秒短版。

## 工作流程

### 1. 先读全量材料

- 从 PPT 提取每页文字，读取讲稿正文；必要时检查备注、图表和页码。
- 建立“已展示事实 / 方案设想 / 未提供数据”三栏清单。
- 标出材料中的高风险词：已实现、自动、优质、准确率、提升比例、全量、直接营销、智能决策等。
- 没有实测数据时，统一改用“计划、设计上、下一步验证、拟采用”，不要替用户补数字。

### 2. 建立评委问题树

至少覆盖以下问题类：

- **真实性**：现在做出来了吗？有没有试点和指标？
- **技术合理性**：为什么多 Agent？数据如何建模？规则如何制定？模型如何验证？
- **系统可靠性**：错配、低置信度、Agent失败、数据质量差怎么办？
- **业务价值**：给客户经理、支行、客户带来什么实际收益？
- **合规边界**：数据授权、隐私、拓客名单、人工复核、审计留痕如何处理？
- **落地路径**：如果只能先做一个功能，先做什么？如何从回放走到试点？

### 3. 技术回答必须说清“怎么做”

遇到“数据建模、专家规则、图数据库、评分、预测、Agent协同”等追问，按以下顺序回答：

1. **对象**：数据里有哪些实体、关系和事件；
2. **结构**：节点、边、字段、证据位置或输入输出如何组织；
3. **方法**：规则、权重、模型或流程具体怎么运行；
4. **校验**：如何处理冲突、低置信度、异常和数据不足；
5. **使用边界**：输出用于辅助分析还是直接决策；
6. **验证方式**：历史回放、人工基线、小范围试点和指标评估。

避免只回答“用大模型分析”“用图数据库存储”“用专家经验打分”。

### 4. 容易混淆的业务场景要拆开

涉及客户数据和拓客时，明确区分：

- **内部分析**：在授权、权限和最小必要范围内处理材料；
- **对客增值服务**：向原客户提供经营分析、资金趋势等服务，需要明确告知并征得许可；
- **外部拓客**：系统只产生内部候选线索，客户经理先核验，再通过客户引荐或其他合法合规渠道接触，不能直接拿流水中的联系方式自动营销。

统一闭环：系统找线索 → 人工核验关系、身份和风险 → 合规渠道接触 → 记录使用过程。没有合法接触依据就不营销。

### 5. 生成答案的固定格式

每题采用：

- **评委问**：保留评委真实口吻；
- **建议答**：先结论，再机制，最后边界或下一步；
- **注意**：指出不能夸大的表述或容易被追问的漏洞。

每组问题末尾增加一条“统一收束句”，帮助参评人在被连续追问时回到主线。

### 6. 文档交付

- 使用清晰的章节：现场节奏、主问题、技术追问、业务追问、合规边界、短答口径、禁用表述。
- 追加用户后来追问的新主题，不覆盖之前已整理内容。
- 生成 DOCX 后必须重新读取文本并运行 DOCX 健康检查。
- 报告中明确“当前方案状态”和“已有实测数据范围”。

## 推荐答题句式

> 先说结论：这是辅助分析，不替代人工决策。具体做法是……结果会保留……遇到异常或权限不足时……目前还没有未经验证的生产指标，下一步通过历史回放和小范围试点验证。

## 常见陷阱

- 把“内部参考名单”说成“自动营销名单”。
- 把“企业是图节点、交易是关系”讲成“一家公司一张数据库表”。
- 把一笔交易直接等同于上下游关系。
- 把方案设计说成已经上线，把预计收益说成实际提升。
- 只谈模型先进，不说明输入、输出、校验、人工责任和失败降级。
- 只说“合规处理”，却不说明名单实际由谁、通过什么渠道、经过什么核验后使用。
