# 图数据库与技术细节现场口径

## 图数据库最容易被问的点

**问：是否为每家公司单独建一个图数据库表？**

建议答：不是一家公司一张表，而是一套统一的交易关系图谱：企业是节点，交易关系是边，金额、时间、频次和方向是关系属性。统一建模便于查询上下游和关联路径，但查询按客户授权和机构权限隔离；系统只输出内部参考线索，不开放全量关系图。

**问：不同公司的流水放在一起会不会混用？**

建议答：逻辑上可以统一建模，但不是无条件混用。节点和关系带来源、授权范围、机构权限和有效期，查询时做权限过滤；高敏感或不同数据域可采用不同图空间或物理隔离。

**问：一笔转账能直接认定为上下游吗？**

建议答：不能。综合交易频率、金额、持续时间、交易方向和多期稳定性形成候选关系，再由业务人员核验。图上的连接只代表存在交易关系，不等于已经确认上下游，更不能直接作为授信或营销结论。

## 数据建模六点式

1. 对象：企业、账户或交易主体、交易事件、材料。
2. 结构：企业做节点，交易做关系或交易事件，金额/时间/方向/频次/来源做属性。
3. 证据：合同、流水、财报字段保留原文位置和材料版本。
4. 校验：主体匹配、重复、时间连续性、异常值、跨文件冲突和低置信度检查。
5. 权限：授权范围、机构权限、最小必要和有效期过滤。
6. 输出：关系候选、风险标签或预测区间，均为辅助分析并可回溯。

## 专家规则口径

先把业务经验拆成可记录的指标、阈值、权重和风险标签，例如交易稳定性、资金集中度和异常波动；每条规则保留依据和版本。冷启动用“规则 + 专家权重”，再用人工复核结果和实际业务结果检验、调整，样本足够后才评估监督模型。

## 技术问题统一收束

先统一数据口径和证据链，用可解释规则完成冷启动，再通过历史回放和小范围试点验证，最后根据样本和效果决定是否模型化。所有结果定位为辅助分析，保留人工复核和既有制度兜底。

## 不要说

- “一家公司一张图数据库表”。
- “一笔交易就是上下游关系”。
- “已经建好全行图数据库”（材料没有这一事实时）。
- “系统自动识别优质客户”或“自动完成授信”。
- 没有实测依据的准确率、效率提升比例。
