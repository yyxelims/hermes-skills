# Grill Me（拷问我）

移植自 `mattpocock/skills` 的 `grilling` / `grill-me`（MIT，236k ⭐）。这是**访谈原语**：在任何人动手之前，把一个方案 / 设计 / 决策拷问到没有隐含假设。

## When to Use（何时触发）

用户说：`拷问我`、`grill me`、`/grill-me`、`挑战我的方案`、`质疑我`、`帮我把这事想清楚`、`stress-test 一下`、`我这个想法有什么问题`。

也在这些时候**主动**用：用户给了一个方案要你直接实现，但里面有多处未说明的取舍；或者一个需求大到你必须靠猜才能开工。

## ⚠️ 本 skill 覆盖"不中途停下问人"的默认偏好

用户的常规偏好是**一口气跑到底、不等人喊继续**。**本 skill 是唯一的例外**：拷问的全部价值就在于每一轮都停下来等用户回答。

- **决策属于用户**，你必须等。自己替用户拍板 = 这个 skill 已经坏了，不是"灵活理解"。
- **前沿清空 ≠ 结束**。结束的标志是用户明确说"达成共识了"。
- 拷问期间不要开始实现。用户确认之后才动手。

## 核心模型：设计树 / 前沿 / 轮次

- **设计树（design tree）**：把主题建模成决策，每个决策下面挂着依赖它的决策。
- **前沿（frontier）**：所有**前置条件已经确定**的决策 —— 也就是此刻你能诚实地问出来、不需要猜任何还没听到的答案的问题。
- **轮次（round）**：一次问完整个前沿，一次全部答完。

做法：**不要一次问一个，也不要一次问全部。**

1. 建出设计树，算出当前前沿。
2. **一轮问完整个前沿**，编号，每题附上你的推荐答案。
3. 停下，等用户回答。
4. 用户的回答确定了一批决策 → 前沿向外推移，解锁下游问题 → **重算前沿**，问下一轮。
5. 前沿为空 → 请用户确认已达成共识。

判据：**如果一个问题的答案依赖本轮另一个还没回答的问题，它属于下一轮，不属于这一轮。** 同一轮里的问题互不依赖，所以本轮任何一个答案都不会推翻本轮另一个问题。

13 个问题通常落在 3 轮左右，而不是 13 轮。

## 提问格式（严格照做）

每题固定形状：`❓` + 编号 + 标题，然后题干，然后**单独一行** `➡️` 给出你的推荐答案。题与题之间用 `---` 分隔。

```
❓ **Q1** — **<问题标题>**：<题干，可以多段，可以给多选项>

➡️ 我的推荐：<你的推荐答案 + 一句理由>

---

❓ **Q2** — **<问题标题>**：<题干>

➡️ 我的推荐：<你的推荐答案 + 一句理由>
```

这个格式的意义：用户可以**按编号回答**（"1 同意，2 选第二个，3 不行，因为…"），不用把问题抄回来。

**已知毛刺**：有时你的推荐会**反对**问题本身的措辞，于是"同意推荐"等于对问题回答"否"。碰到这种情况，用户按推荐回答并说明即可 —— 你要能识别这种回答。

## 事实归你，决策归用户

这是本 skill 的另一半设计，也是最容易做坏的地方。

- **事实（facts）是你的活，永远不是用户的活。** 前沿上的问题需要环境里的事实（文件内容、代码结构、库版本、接口是否存在、数据实际长什么样），就自己去查：`read_file` / `search_files` / `terminal`，量大或需要独立探索时用 `delegate_task` 派子 agent。**绝不要问用户你自己能查到的东西。**
- **不要因为查事实而阻塞。** 正在跑的探索 = 一个还没确定的前置条件，所以只有它下游的问题需要等；前沿上其余问题现在就问。
- **决策（decisions）是用户的。** 逐条摆到用户面前，然后等。

## 收尾

前沿为空 = 设计树每个分支都走过了，没有任何东西被默默假设。此时**不要动手**，先请用户确认"我们已经达成共识"。用户确认后才实施。

## 坑（来自上游实战反馈）

| 坑 | 说明与对策 |
|---|---|
| **前沿是判断，不是算出来的图** | 你可能把两个问题放进同一轮，事后才发现其中一个答案本该改变另一个。没有自动防护 —— 用户指出后，下一轮重开受影响的分支。 |
| **弱模型 / 低算力档把拷问坍缩成"问两句 + 给个大纲"** | 这是 bug 不是简化。坚持轮次 + 前沿 + 每题带推荐。 |
| **在"帮我解决这个工单"的框架里跑拷问，容易被当成可以继续往下做的许可** | 不行。拷问期间只问不做。 |
| **没有次数上限，且刻意不设** | 有的方案 3 个问题够了，有的要 50 个。用户用自然语言控制（"收尾吧"/"就这样"）。如果一轮接一轮跑不完，通常说明范围太大 —— 把工作拆开，分块拷问。 |
| **没有异步模式** | 一个没人回答的拷问产出的是**你的**意见，不是用户的意见。那是另一回事。 |

## 何时该用别的东西

| 情况 | 换用 |
|---|---|
| 光靠谈定不下来的问题（某个东西该长什么样、什么手感） | 先做一次性原型（`sketch` / `spike` skill），再回来拷问 |
| 大到一个会话装不下的工程 | 先拆分（`writing-plans` skill），再对每块分别拷问 |
| 已经想清楚了，只要落地计划 | `writing-plans` |
| 已经写完了代码，要挑毛病 | `requesting-code-review` / `ponytail-review` |

## 语言

用用户说话的语言拷问。中文对话就全程中文，包括 `➡️ 我的推荐`。
